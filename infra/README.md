# Переезд на свой сервер

Всё, что нужно для переноса базы и входа с чужих серверов на свой в России.
Порядок написан так, чтобы на каждом шаге было понятно, **что проверить**, —
почти все поломки при таком переезде тихие: выглядит работающим, а не работает.

Сайт остаётся на Vercel. На сервер переезжают база, вход и сервер приложений.

## Что где будет

| Адрес | Что там | Откуда переезжает |
|---|---|---|
| `aiservicemarket.com` | сайт | Vercel, остаётся |
| `auth.aiservicemarket.com` | Supabase: вход, база, файлы | Supabase Cloud (Франкфурт) |
| `api.aiservicemarket.com` | сервер приложений | Render |
| `id.aiservicemarket.com` | Keycloak: вход через Яндекс | новое |

Панель Supabase Studio наружу не открывается — только через SSH-туннель.

## Что нужно до начала

- VPS: **4 ядра, 8 ГБ памяти, 80 ГБ NVMe**, Ubuntu 24.04. Меньше 4 ГБ не хватит:
  Postgres, Supabase, Keycloak на Java и Nginx в покое занимают около 4 ГБ.
- Домен переведён на Vercel, три поддомена (`auth`, `api`, `id`) указывают A-записью
  на адрес сервера.
- Приложение в Яндекс OAuth: https://oauth.yandex.ru/client/new
- Почтовая служба с настроенными SPF, DKIM и DMARC. Для России — Unisender Go или
  SendPulse: до Mail.ru и Яндекс.Почты они доходят заметно лучше западных.

## Порядок

### 1. Сервер

```sh
apt update && apt install -y docker.io docker-compose-v2 nginx certbot python3-certbot-nginx
ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw enable
```

Наружу открыты только 22, 80 и 443. Postgres, Keycloak и сервер приложений
слушают `127.0.0.1` — снаружи к ним доступа нет вовсе.

### 2. Supabase

```sh
git clone --depth 1 --branch self-hosted/v0.8.0 https://github.com/supabase/supabase
mkdir supabase-project && cp -rf supabase/docker/. supabase-project
cd supabase-project && cp .env.example .env
```

Затем перенести в `.env` значения из `infra/.env.example` этого репозитория
и сгенерировать секреты (`openssl rand -base64 48`). **Пароли по умолчанию не
оставлять** — сборка поднимается с открытыми учётными данными.

### 3. Почта — до первого входа

В стандартной сборке стоит **Inbucket**: ловушка, которая принимает письма и
никуда их не отправляет. Выглядит как рабочая почта. Заменить настоящим SMTP.

Проверка: отправить письмо для входа на **три** адреса — Gmail, Mail.ru и
Яндекс.Почту — и посмотреть не только «пришло ли», но и **не в спаме ли**.

Ещё две тихие поломки: без `API_EXTERNAL_URL` рядом с `SITE_URL` ссылки в
письмах приходят битыми; без адреса возврата в `ADDITIONAL_REDIRECT_URLS`
переход по ссылке заканчивается ошибкой.

### 4. Keycloak — вход через Яндекс

```sh
./infra/scripts/fetch-keycloak-plugin.sh
docker compose -f docker-compose.yml -f docker-compose.override.yml up -d keycloak
docker compose exec keycloak /opt/keycloak/bin/kc.sh build
```

Дальше в панели Keycloak: создать realm `aimarketplace`, добавить провайдера
Яндекс (появится из плагина), вписать ключи приложения, создать клиента
`ai-marketplace` и его секрет положить в `GOTRUE_EXTERNAL_KEYCLOAK_SECRET`.

Почему так, а не напрямую: список провайдеров в самостоятельной сборке Supabase
зашит жёстко, Яндекса и VK там нет и не появится. Keycloak делает из них один
вход, который Supabase понимает.

### 5. Перенос данных

```sh
SOURCE_DB_URL='...' ./infra/scripts/export-from-cloud.sh
# на сервере, по очереди:
psql "$TARGET" -f roles.sql
psql "$TARGET" -f schema.sql
psql "$TARGET" -f data.sql
```

Что произойдёт с людьми:

- **Пароли переносятся** — хранятся хешами, они переезжают как есть.
- **Все сессии обнулятся** один раз: ключ подписи новый, значит все выйдут из
  аккаунта и войдут снова. Это ожидаемо, не поломка.
- **Вход через Google сохранится**, если использовать тот же Client ID и
  добавить в Google Console новый адрес возврата. С другим ID люди при входе
  получат новую пустую учётную запись вместо своей.

### 6. Переключение сайта

В настройках Vercel заменить `NEXT_PUBLIC_SUPABASE_URL` на
`https://auth.aiservicemarket.com`, ключ — на новый, `NEXT_PUBLIC_API_URL` — на
`https://api.aiservicemarket.com`, и выложить заново.

Код клиента при этом **не меняется**: и `@supabase/ssr`, и проверка токена на
сервере работают с самостоятельной сборкой один в один.

### 7. Резервные копии — в тот же день

В облаке их делал Supabase. Теперь это ваша обязанность, и день, когда об этом
вспоминают, обычно наступает поздно.

```sh
0 4 * * * docker compose exec -T db pg_dump -U postgres postgres | gzip > /backup/db-$(date +\%F).sql.gz
```

Хранить **не только на этом же сервере** и раз в месяц проверять, что копия
разворачивается. Непроверенная копия — это не копия.

## Проверка, что переезд удался

1. Регистрация по почте с паролем — письмо дошло не в спам, вход работает.
2. Вход через Google — открывается прежняя учётная запись, не новая.
3. Вход через Яндекс — создаётся учётная запись.
4. Сброс пароля — ссылка из письма открывается и меняет пароль.
5. Каталог `/browse` открыт гостю (проверить на `/api/health`).
6. Чат: сообщение доходит второму участнику без перезагрузки страницы.
7. Загрузка аватара сохраняется и открывается по ссылке.
